Type-word glossary

Definitions from the May 2026 "My statement on workflows" document. Used consistently in Jira component names, docs titles, and article headings.

Type wordDefinition and testExamples
Integration A background relationship between SpecterX and an external system for exchanging data, identity signals, or policy/classification metadata. Test: if you removed it, would a normal user notice immediately or would things just silently get worse? Entra ID Integration, Opswat CDR Integration, DLP Mailflow Integration
Connector A user-facing surface where the user actively does something through SpecterX into a specific third-party app. Test: does the end user click a button that mentions the third-party app by name? Google Drive Connector, Slack Connector, Salesforce Reports Connector
Add-in Microsoft's term. Code that runs inside a Microsoft Office host application. Use for anything that runs inside Outlook, Word, Excel. Outlook Classic Add-in, Outlook New Add-in
Extension The browser ecosystem's term. Code that injects into a web page or browser chrome. Use for anything that runs inside Gmail, Chrome, Edge, Salesforce in-browser. Gmail Extension, Salesforce Browser Extension
Engine The renderer/processor underneath a SpecterX product surface. Test: could you swap it for a different vendor's technology without the customer noticing? SpecterX WOPI Host, SpecterX Office Viewer (engine), SpecterX PDF Viewer (engine)
Open-With Target A third-party app the user chooses to open a SpecterX-protected file in, where the file leaves SpecterX's rendering context. Test: does the user pick this from an "Open with…" menu and does the file get handed off? Open with Adobe Desktop, Open with Native Office, Open with Microsoft Edge
Service The backend SpecterX operates to power a feature. Internal-facing word. Only split Client + Service when the two have genuinely separate deployment/release/ownership cycles. Mail Protection Server (deployed), Mail Protection Service (cloud)
Policy Protection A file-level security measure that admins enable through the policy management UI, applied automatically to files governed by that policy. Test: is this configurable per-policy in the policy editor? Watermarking, Password, Encrypt using Rights Management
Gateway A self-contained SpecterX deployment that runs in a customer's environment, rather than in SpecterX's cloud. The deployment model (release cadence, support, version skew) is fundamentally different from cloud. SpecterX Gateway (On-Prem), SpecterX Gateway Storage Connector (On-Prem)

SpecterX article skeleton

Synthesized from the four reference platforms. Every SpecterX article should follow this structure.

Skeleton (every task page)
Breadcrumb (Section › Article)
H1  <Verb> <object> sentence-case
1-paragraph intro (what + why)
H2  Before you get started
   Requirements
   Permissions required
H2  In this article (TOC, skip if short)
   [Important: callout — supported formats/limitations
    with inline cross-links to related concepts]
H2  <Primary task #1>
   Numbered steps, bold UI labels
   Screenshot after each major step
H2  <Primary task #2>
H2  Recipient experience (when applicable)
H2  Related articles (3–4 sibling cards)
Voice rules (from HubSpot + DocSend)
Strict 2nd person ("you"). No "the user".
Bold every UI label: Share files, Contributor.
Sentence-case headings.
Spell out the full product name on first reference.
"Before you get started" is the universal first H2.
Lifecycle status callouts inline (maintenance mode, beta).
Length & screenshots (from Egnyte + DocSend)
Target 800–1,500 words per article.
5–10 screenshots per task page.
Landing pages: ≤3 screenshots.
Screenshot immediately below each step.
Crop to the panel, not the full window.
Related articles: 3–4 sibling cards (DocSend pattern).

IA design decisions

Decision Rationale Reference precedent
Section names use verb-phrase convention "Share files", "Receive files", "Send protected email", "Configure security policies", "Manage your organization" — each title names the user's job, not the feature name. Consistent imperative form throughout. DocSend: "Managing spaces", "Securing your data" — category names describe the user's job, not the feature
Per-connector lifecycle pages; no shared cross-connector install hub SpecterX users know their email client before they start. A user with Outlook searches for "Outlook add-in", not "which connector should I install?". Each connector gets its own landing + verb-split lifecycle (Set up / Send / Track / Troubleshoot / Uninstall). The cross-connector decision page HubSpot needs does not apply here. HubSpot §0 lifecycle pattern adapted: keep per-connector pages, drop cross-connector hub
Each Policy Protection gets its own article with verb-first title Same UI panel but distinct security models and recipient experiences. "Add a watermark to protected files" not "Watermarking". Verb-first titles are searchable and action-oriented. Clarity over consolidation. DocSend: email authentication vs email validation as separate pages; HubSpot: action-titled headings
"Apply a policy when sharing" bridges admin and end-user perspectives Policies can be applied to files, folders, workspaces, and email attachments — each context has slightly different UX. One article covers all four, with H2 per context, cross-linking to the Configure a security policy admin article and to individual policy-protection articles. Egnyte: separate User Guide and Config Guide for the same feature
§3 "Receive files": email OTP inline; SMS and personal secret as supplementary articles The main "Open a SpecterX-protected file" article covers the common case (email OTP). "Verify with SMS" and "Verify with a personal secret" are separate supplementary articles because their flows are meaningfully different (phone registration, different UI path). Split when flows differ; consolidate when they don't. Virtru: "Using SMS for secondary verification" as a separate article; DocSend: split when different end-states
§11 Reference & limitations: per-capability limitations articles with inline cross-links Each capability (watermarking, password encryption, RMS, block download) gets a dedicated limitations reference article. Format follows DocSend's watermarks page: prominent "Important:" callout at the top of the body stating supported file types, with inline hyperlinks to articles that explain the excluded scenarios (e.g. "Download-only files" links to the download reference). DocSend: "Important: only PDFs, Keynotes, PPT, Word can be watermarked. Download-only files and URL uploads can't." — with cross-links; Vera: top-level Constraints section
Limitations callout placed after "In this article" TOC, not inside "Before you get started" "Before you get started" = what you need in order to perform this task. The limitations callout = scope of what the feature does and does not cover. These are different questions; DocSend's placement (callout after TOC, before first task H2) keeps them appropriately separate. DocSend watermarks page: Important callout appears after "In this article" TOC
Mail Protection setup moved from §5 to §9 §5 "Send protected email" contains end-user sending actions. Mail Protection for Exchange Online / Google Workspace / Cisco SEG is admin infrastructure setup. All 5 reference platforms place gateway/mailflow admin setup in admin/integration sections, separate from user send docs. Moving Mail Protection to §9 makes §5 purely end-user content. Virtru: admin deploy docs in "Virtru for Admins > Install & Deploy"; Egnyte: Outlook User Guide vs Config Guide split
Connector quick-start landing pages live in §5, not §1 "SpecterX for Outlook — quick start" is a connector landing page (product description + lifecycle links). All 5 reference platforms place connector landing pages inside the connector's own section, not in a global "Get started" area. §1 "Get started" should be product-wide orientation only. HubSpot: "Set up the Chrome extension" is section-level, not global; Virtru: "Get started with Virtru for Outlook 365 Add-in" is first article in the Outlook sub-section
Connector disambiguation FAQ article in §5 "Outlook Classic vs Outlook New Add-in — which should I use?" answers the install-decision question without a shared install hub. Scales cleanly as Classic enters maintenance mode. Each connector then has its own lifecycle articles. Virtru: "What is the difference between Virtru's Outlook 365 Add-in and Outlook Desktop Extension?"
Supplementary verification articles in §3 for non-default flows The main recipient article covers the common case (email OTP). "Verify with SMS" and "Verify with a personal secret" are separate supplementary articles because their flows are meaningfully different (phone registration required; different UI path). Linked from the main article. Virtru: "Using SMS for secondary verification" as a separate article from the main recipient flow
§10 Gateway uses About → Prerequisites → Install → Post-install → Reference skeleton Consistent article set per deployable product. Readers know exactly what to expect. Mirrors enterprise deployment docs pattern. Virtru "Advanced Products" — each gateway/keystore product uses this exact 5-article structure
§11 includes per-framework compliance articles and per-product release notes Enterprise customers search by compliance framework name (HIPAA, GDPR). Release notes in Reference keeps the main nav clean and prevents version noise in product sections. Virtru: "Compliance & Legal" section (HIPAA, CJIS, FERPA, FIPS); per-product Release Notes in Billing & More
Always show breadcrumbs Users land via search and need immediate orientation. HubSpot and Egnyte skip breadcrumbs; we do not. HubSpot "Patterns NOT to copy" §2
Inline "Related articles" footer (3–4 cards) for lateral discovery Sibling articles in the same section are the most likely next read. Cards (heading + snippet) surface them without forcing the reader back to the section index. DocSend "Related Articles" card footer
